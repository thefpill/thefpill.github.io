Basically to gather metadata from each `HEAPENTRY32` struct that I got from my version of `HeapWalk` -  Heap32First/Next with VirtualQueryEx on top to get additional info about page attributes that contain that block 

Important distinctions when moving forward : 
- Heap metadata describes a heap block.
- Virtual-memory metadata describes the pages containing that block.
- Memory contents describe the bytes currently readable at that address.

But oh boy! Thinking scanning the memory will be easy was a big overestimation. Here is just a quick rundown of concepts I had to (somewhat)  learn along the way.

VAD **(Virtual Address Descriptor)** -> as kernel mode data structure ( source of truth - when not dealing with kernel level exploits ). Detecting in-memory attack vectors 

**PEB** ->  forensic significance. Why relying on CreateToolHelp32Snapshot is a cool convenient way but abstracts critical information needed for proper forensic investigation. 

**Heap** -> Multiple heaps per process. Different heap types `NT`/ `Segment`. `Heap Segments` linking between them, `heap entries` and  challenges walking heap entries in different heap types. 


This is just few concepts we will be in one way or another diving deeper into so stay tunned!

But deeper I got the more I realized that using Heap32First/Next wasn't really going to cut it ... maybe I should have done better research beforehand - oh well time to rewrite the whole heap parsing logic.
